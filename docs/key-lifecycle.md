# Керування життєвим циклом ключів

## Генерація

1. Користувач вводить унікальну парольну фразу (не менш як 12 символів; практично краще довшу випадкову фразу).
2. Система отримує `salt = secrets.token_bytes(16)` з криптографічно стійкого генератора; створює випадковий `key_id` з 12 байтів.
3. `PBKDF2-HMAC-SHA256` із **600 000** ітерацій похідними генерує матеріал для ключа AES (16, 24, 32 байти), окремого HMAC (32 байти) і ключа перевірки пароля (32 байти).
4. `keystore.json` зберігає лише id, label, salt, параметри KDF, timestamp, usage, status і HMAC-перевірку правильності пароля. *Сирий симетричний ключ і пароль не серіалізуються.*
5. На POSIX файл створюється з правами `0600`; `.gitignore` виключає його з репозиторію.

**Чому salt важливий:** при ротації навіть із тією ж парольною фразою ключові байти будуть іншими. Унікальність ключа забезпечується випадковим salt; лише повторення паролю без повторення salt не означає повторення ключа.

## Використання

- Нові файли шифруються тільки активним ключем; у заголовок включено випадковий IV/nonce і `key_id`.
- Для AES-GCM 96-бітний nonce генерується CSPRNG для **кожного** файлу; модуль не дозволяє користувачу задавати статичний nonce. За великих масштабів потрібен формалізований контроль колізій і обсягу шифрування.
- Для CBC/CTR використовується випадковий 128-бітний IV. Усі режими автентифікують заголовок; CBC/CTR також автентифікують шифртекст HMAC.
- Після успішного шифрування лічильник `uses` збільшується. Через 100 використань чи 90 днів нове шифрування блокується до ротації. Числа — **локальна політика демонстрації**, а не нормативні ліміти AES.

## Ротація

`python aes_cli.py key rotate --label default`

Поточний ключ переходить у стан `retired`; створюється нова пара salt/key_id із новими похідними ключами. Старий ключ неможливо застосувати для **нового шифрування**, але можна дешифрувати його старі файли за вказаним у заголовку key_id. Видалення старого запису до завершення міграції призведе до втрати можливості дешифрування.

## Відновлення / архівування / компрометація

- Резервне копіювання `keystore.json` і зашифрованих файлів — окремі захищені копії; пароль зберігати в окремому менеджері секретів.
- При компрометації пароля: ротація з **новою** парольної фразою (автоматичний `rotate` в поточній реалізації використовує ту саму фразу; для зміни треба перевипустити ключ і мігрувати файли), повторне шифрування даних, перевірка журналів, відкликання доступу.
- Немає захисту від фізичного видалення ключових метаданих, зламу робочої станції або офлайн-перебору слабкого пароля. Для експлуатації потрібні KMS/HSM та регламент резервних копій.

**Джерело:** [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) рекомендує PBKDF2-HMAC-SHA256 із 600 000 ітерацій для певних сценаріїв зберігання паролів. Для лабораторії це обрано як базову консервативну конфігурацію похідної, а не як стандартну універсальну норму для всіх ключових сховищ.
